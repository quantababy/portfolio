## Overview

VeritasChain is a decentralized AI fact-checking system designed to make claim verification more structured, evidence-driven, and auditable.

Instead of treating fact checking as a single LLM request, the system combines DSA-based claim processing, verification orchestration, RAG-based evidence retrieval, source-trust analysis, and blockchain/IPFS-backed audit records.

The project is designed around an end-to-end verification workflow. Each stage has a defined responsibility, from processing the incoming claim and retrieving supporting evidence to generating a structured verification result and preserving an auditable record.

## Architecture

The high-level workflow is:

![VeritasChain system workflow showing the DSA engine, AI agent, LLM and RAG pipeline, GNN source-trust engine, and blockchain audit layer](/projects/veritaschain/workflow.png)

### DSA processing engine

The DSA processing layer handles the organization and processing of incoming claims before they move through the verification pipeline.

This layer provides deterministic processing logic around the AI components, helping separate data and claim processing from model inference.

### Verification and orchestration

The verification layer coordinates the individual stages of the fact-checking workflow.

LangGraph and LangChain are used to structure the verification process and connect claim processing, evidence retrieval, model inference, and downstream result handling.

This keeps the overall workflow modular rather than embedding every operation inside a single model call.

### RAG and evidence retrieval

The evidence-retrieval layer uses retrieval-augmented generation to find relevant supporting information for a claim.

FAISS provides vector-based retrieval so that relevant evidence can be surfaced before the language model generates the verification result.

The purpose of this layer is to ground the verification process in retrieved evidence rather than relying only on information generated by the language model.

### Source-trust graph

The source-trust layer models relationships between sources and uses graph-based processing to incorporate source relationships into the verification workflow.

PyTorch Geometric provides the graph machine-learning layer used for this component.

The source-trust system is intended to provide additional context around the reliability and relationships of evidence sources rather than acting as a standalone fact-checking model.

### Backend and real-time layer

FastAPI provides the backend API layer.

PostgreSQL stores structured application and verification data, while Redis supports transient or asynchronous processing requirements.

WebSockets provide real-time communication between the backend and frontend during verification workflows.

The frontend is implemented using React and TypeScript.

### Blockchain and IPFS audit layer

Solidity and Web3.py provide the blockchain integration, while IPFS is used for content-addressed storage.

The blockchain layer is used as a persistence and audit mechanism for selected verification records and associated artifacts.

Blockchain is therefore treated as an audit layer rather than as the computational engine of the fact-checking workflow.

## Engineering decisions

### Separate deterministic processing from AI inference

The system separates DSA-based claim processing from LLM-based verification.

This makes the deterministic processing layer independently maintainable while allowing the model and retrieval components to evolve without redesigning the complete workflow.

### Retrieval-assisted verification

RAG was used so that verification can incorporate retrieved evidence rather than depending entirely on the language model's internal knowledge.

FAISS provides the vector retrieval layer used to surface relevant evidence.

### Graph-based source analysis

A graph-based approach was selected for source relationships because source trust can involve relationships between multiple sources rather than a single isolated score.

PyTorch Geometric provides the graph-processing infrastructure for this part of the system.

### Modular verification workflow

LangGraph and LangChain are used to organize the verification stages into a structured workflow.

This makes the individual processing stages easier to reason about and replace.

### Auditability

Blockchain and IPFS were included to provide a persistent audit layer for selected verification records and associated artifacts.

The design keeps the expensive computational work off-chain while using blockchain for the persistence and auditability requirements.

## Results

The completed system demonstrates an end-to-end architecture for AI-assisted fact checking:

- Claims can be processed through a dedicated DSA layer.
- Relevant evidence can be retrieved through a RAG pipeline.
- An LLM can use retrieved evidence to produce a structured verification result.
- Source relationships can be processed through a graph-based trust layer.
- FastAPI and WebSockets provide the application and real-time communication layers.
- Selected verification records can be persisted through the blockchain/IPFS audit layer.

No specific accuracy, latency, throughput, or performance percentage is claimed here because the project does not include a published benchmark supporting those numbers.

## What broke / constraints

Building a multi-stage AI verification pipeline introduces several practical constraints.

Retrieved evidence quality directly affects the usefulness of the final verification result. A retrieval system can only provide useful grounding when relevant evidence is available in its underlying knowledge source.

LLM-generated verification results can also require additional validation because the model remains capable of producing incorrect conclusions even when retrieval is available.

The graph-based source-trust layer introduces additional modeling and data requirements because useful source relationships need to be represented consistently.

The blockchain/IPFS layer adds infrastructure complexity and should therefore be used selectively for auditability rather than for every intermediate computation.

Another constraint is that blockchain persistence is not intended to replace the application database or the verification pipeline itself. It serves a narrower role as an audit and persistence mechanism.

## Next

Potential future work includes improving evidence retrieval and ranking, expanding the source-trust graph, introducing stronger evaluation datasets, improving verification-result explanations, and adding more systematic benchmarking of the complete pipeline.

Additional work could also explore richer provenance records so that individual verification results can expose the evidence and source relationships that contributed to the final result.
